# a19 | Agent 評估與可觀測性：沒有軌跡與評估集，就不要談上線

> 來源：`lectures/A19 Agent 評估與可觀測性 投影片.pdf`（共 40 頁；講義日期 2026-10-29；出處為 Amazon Bedrock AgentCore Observability／Evaluations）

**今日目標**：週五 demo 過關、週三客訴才發現提示詞改壞了。學會留軌跡、從失敗長評估集、用五類指標與門檻，把評估接進 CI。

**貫穿例子**：阿芯豆花店客服。問題是「改提示詞之後，已出貨訂單還會不會被誤取消？」答案必須來自軌跡與評估集，不能來自感覺。

## 一、為什麼難測：過程與結果都要看

**失敗故事**：週五 demo 未出貨可取消 → 週一改提示「更友善」→ 週三客訴已出貨被取消。根因：沒有回歸題擋住 A1042 已出貨路徑。**展示成功 ≠ 可上線**。

| 難測理由   | 說明                                     |
| ---------- | ---------------------------------------- |
| 輸出是分布 | 同一題跑兩次，文字可以不同               |
| 錯在中間輪 | 最終答案漂亮，工具早叫錯了               |
| 失敗不丟例外 | HTTP 200 也能禮貌地講錯                |

**傳統 API vs Agent**

| 項目     | 傳統 API         | Agent              |
| -------- | ---------------- | ------------------ |
| 輸出     | 可比對           | 是分布             |
| 錯誤     | 例外會冒泡       | 錯誤藏在禮貌句     |
| 測試     | 比對字串         | 要覆蓋過程         |

> 一句話：Agent 難測，因為過程與結果都可能錯，承認難測才會投資軌跡與評估集。

## 二、執行軌跡：病歷不是出院證明

**為什麼一定要留**：除錯（沒有時間線只能猜哪一步壞）、評估原料（真實失敗進評估集，軌跡是證據）、成本與延遲（token 與耗時也是產品指標）。

**時間線**：提示 → 模型 → 工具 → 結果 → 再模型 → 答案（對應 OTEL，AgentCore Observability）

**軌跡最小欄位（沒有這些就等於沒記）**

| 欄位                | 說明             |
| ------------------- | ---------------- |
| tool name           | 叫了誰           |
| args summary        | 參數摘要（遮罩） |
| latency／tokens     | 延遲與用量       |
| result summary      | 結果摘要（遮罩） |

- 結果與參數**遮罩後再存**，勿傾倒原文（個資、機密）

**四種分岔：先定位失敗類型（對應 A17 失敗模式）**

| 分岔       | 豆花例                              |
| ---------- | ----------------------------------- |
| 沒叫       | 該查單卻直接答                      |
| 叫錯       | 該查規卻 cancel                     |
| 參數錯     | `order_id` 填成電話                 |
| 生成沒用   | 工具對、回覆瞎編                    |

- 讀軌跡：先找分岔點 → 標類型 → 真實失敗才進評估集

> 一句話：沒有軌跡就沒有除錯權；欄位要齊、要遮罩、要能回放。

## 三、評估資料集：從失敗長題目

**為什麼要從失敗長**：開心路徑不夠（demo 題測不到客訴）；空題沒鑑別力（兩百題假題不如二十題真痛）；回歸要有牙齒（改提示時痛題必須擋住）。

**題目從哪來**：客訴（最痛優先）、死信（A13 的 DLQ 當原料）、軌跡（補過程）

**評估題三欄**

| 欄位   | 說明               |
| ------ | ------------------ |
| input  | 使用者原話         |
| expect | 期望行為（寫死）   |
| score  | 怎麼判定           |

**範例：已出貨不該取消**：input 為 A1042 已出貨被 `cancel_order`；期望拒絕或查物流；判定「禁 cancel；須引出貨狀態」。痛苦變成回歸資產，改提示必過。

**從一筆客訴變成一題**

1. 複製使用者原話當 input（不要美化成教科書句子）
2. 寫期望行為與禁止行為（例如禁止呼叫某工具）
3. 選判定方式（能程式判就不要只靠模型評）
4. 附上當次軌跡摘要（方便以後除錯對照）

> 一句話：評估集是痛點的標本館，不是題目產生器的垃圾桶；先求真，再求多。

## 四、核心指標：五類一起看

**五類**：任務完成率、工具正確率、有據性、延遲、每次成本。

**豆花客服門檻示例（課堂示例，供討論，不是官方標準）**

| 指標     | 門檻                       |
| -------- | -------------------------- |
| 完成率   | 退貨詢問 ≥ 90%             |
| 工具正確 | 已出貨禁 cancel ≥ 99%      |
| 有據性   | 含規則引用 ≥ 95%           |
| 延遲     | p95 < 8 秒                 |
| 成本     | 每次 < $0.05               |

| 類型   | 超標時                 |
| ------ | ---------------------- |
| 硬門檻 | 不過不得部署           |
| 軟目標 | 只警報                 |

- **開會先印表**，避免趕進度時臨時關掉門檻

**迷思澄清框**

**有儀表板就等於有評估？**

- ✗ 雲端觀察面板綠燈，就代表品質可以上線
- ✓ 觀察讓你看得到；評估才對門檻做判定並擋住部署

> 一句話：五類指標缺一格就是盲飛，硬門檻要印在部署流程上。

## 五、模型評分者：助理不是法官

| 判定方式 | 用在                         |
| -------- | ---------------------------- |
| 程式判定 | 工具對錯                     |
| 模型評分 | 語意要點（LLM-as-a-Judge，AgentCore Evaluations） |
| 人       | 抽查與校準                   |

**校準**：人先評 10 題當金標 → 模型評同題 → 比對分歧 → 分歧高就改規準。**評分規準要寫死，分歧高的面向不要一票決。**

> 一句話：工具對錯用程式，語氣用人校準，模型評分者是助理不是終審。

## 六、評估進 CI：紅燈就不能部署

- 流程：變更 → 跑評估集 → 比門檻 → 通過才部署；**提示或模型變更必觸發**

| 項目 | 觀察（Observability）  | 評估（Evaluation）         |
| ---- | ---------------------- | -------------------------- |
| 作用 | 看得到發生什麼         | 對門檻做判定               |
| 能否擋部署 | 不能             | 可以                       |
| 綠燈 | ≠ 品質合格             | 通過才放行                 |

**Quiz**：把 Agent 從能展示變成能上線，最不可缺 → **可回歸的評估集與軌跡**；華麗提示、更多角色（更難測）、更貴模型都不是。

> 一句話：難測要承認，失敗要進題庫，門檻要擋部署。

## Takeaway

1. Agent 難測，因為過程與結果都可能錯；展示成功不等於可上線
2. 軌跡欄位要齊、要遮罩、要能回放；先找分岔點再定失敗類型
3. 評估集從客訴、死信、軌跡長，三欄：input、expect、score
4. 五類指標缺一格就是盲飛；硬門檻擋部署，評估進 CI
