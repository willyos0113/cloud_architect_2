# a18 | 多 Agent 與 MCP：先問要不要拆，先把工具描述寫對

> 來源：`lectures/A18 多 Agent 與 MCP 投影片.pdf`（共 45 頁；講義日期 2026-10-29；出處為 Anthropic〈Building effective agents〉、Model Context Protocol Specification、Bedrock Agents 開發者指南）

**今日目標**：四個 Agent 開會，常常比一個 Agent 加三個工具更慢。先問為什麼一定要拆，再談拓撲、脈絡隔離、MCP 與工具描述怎麼寫。

**貫穿例子（A18→A19→A20）**：阿芯豆花店客服。顧客問「訂單 A1042 的冷藏豆花能不能退？」客服要查訂單狀態、查退貨規則、必要時拒絕或轉人工，最後寫一句有證據的回覆。

---

## 一、何時不要拆：單迴圈加工具先做完

**三件事**

- 單迴圈是預設（A16／A17 的做法），先證明單 Agent 撞牆再拆
- 多 Agent 是為了**隔離**，MCP 是為了**接口重用**
- 先講何時不該拆，比背拓撲名字更像有經驗

**豆花客服現況**：一個 LLM 迴圈加三個工具（`get_order`、`lookup_policy`、`cancel_order`），問句 → 選工具 → 回對話 → 回覆。

**拆了之後，四筆帳一起變大**

| 帳   | 說明                         |
| ---- | ---------------------------- |
| 協議 | 交接協議要寫死               |
| 延遲 | 每多一棒多一輪模型呼叫       |
| 費用 | 多一棒就多一輪模型費         |
| 除錯 | 變成多條軌跡、交接錯         |

**值得拆的三閘門（都過才拆）**

| 閘門   | 問題                                   | 豆花例                         |
| ------ | -------------------------------------- | ------------------------------ |
| 隔離   | 提示會不會互相污染？                   |                                |
| 權限   | 權限能不能共用？                       | 退款權限與判定提示要切開才值得拆 |
| 可驗證 | 交接內容能不能機器驗證？               |                                |

**迷思澄清框**

**多開幾個 Agent，像請更多同事，一定比較強、比較穩嗎？**

- ✗ 大家通常會想：多開幾個 Agent 像請更多同事，一定比較強
- ✓ 實際上：多 Agent 的價值是切開誰能看什麼、誰能做什麼；不是模擬公司組織圖

> 一句話：能用工具解決，就先不要用人形角色解決。

## 二、四種拓撲：誰決定下一步

| 拓撲                | 控制權               | 適合                     | 可測性 |
| ------------------- | -------------------- | ------------------------ | ------ |
| 主管（Supervisor）  | 中央調度，主管決定叫誰、何時結束 | 路由多、角色固定  | 好追   |
| 交接（Handoff）     | 做完交棒，每棒交結構化摘要，收件先驗證 | 上下游有品質門檻（檢索 → 生成 → 引用檢查） | 中 |
| 循序（Pipeline）    | 固定順序（查 → 判 → 回） | 步驟固定、要進 CI    | 最好測 |
| 群集（Swarm）       | 互相呼叫             | 探索原型                 | 難追，路徑會爆炸 |

- 選拓撲先問：**誰有權決定下一步？控制權越集中越好測**
- 群集上線前要把控制權收斂，否則出事時不知道誰叫誰
- 豆花例：A1042 步驟固定 → 用循序；交接只交 `order_id`＋`evidence`

> 一句話：路由多用主管，固定步驟用循序，品質門檻用交接，群集留給原型。

## 三、脈絡隔離：價值在切開脈絡

**為什麼隔離比「模擬團隊」重要**

| 風險       | 說明                                       |
| ---------- | ------------------------------------------ |
| 提示會污染 | 作者的提示若被審稿者看到，審稿容易放水     |
| 權限會外溢 | 全共享對話時，退款工具可能被讀頁角色碰到   |
| 視窗有上限 | 每個角色的脈絡都要刻意變瘦                 |

- 做法：各看各的，只交摘要。豆花例：判定者不要看到內部成本欄位
- 隔離後審稿只看正文＋引用清單，不看作者提示

**交接物：短、結構化、可驗證（像內部 API 的回應）**

```
order_id: A1042
evidence: D01 / D04
next: generate_reply
```

- 禁止：思考過程、成本、員工備註

**設計交接物四步**

1. 列出下一棒真正需要的欄位（只留能開工的最小集合）
2. 每個欄位寫驗證規則（缺了或格式錯就退回）
3. 列出禁止欄位（思考過程、成本、員工備註）
4. 用一筆真實案例試交（看收件方能不能只靠交接物開工）

**Quiz**：導入多個 Agent 最合理的主要理由 → **把不同角色的脈絡與權限隔開**；擬人化組織圖不是工程目標，通常更貴更慢。

> 一句話：隔離才拆，交接物要短、結構化、可驗證。

## 四、MCP：一套協議接工具

**為什麼需要 MCP**

| 原因       | 說明                                               |
| ---------- | -------------------------------------------------- |
| 插件碎片化 | 每個助理各寫一套工具插件，維護成本爆炸             |
| 契約可重用 | 同一台工具伺服器可被 IDE、聊天室一起接             |
| 安全有共識 | 規格要求宿主處理同意；工具等於任意程式執行         |

**三個角色與三種能力**

| 角色   | 說明                                  |
| ------ | ------------------------------------- |
| Host   | 宿主，如客服聊天室、IDE               |
| Client | 連線                                  |
| Server | 暴露 **Tools／Resources／Prompts**    |

- 通訊用 JSON-RPC；描述一次、多宿主重用

**Tools 往返四步（A1042 查單）**：`tools/list`（發現）→ 模型選擇 → `tools/call`（執行）→ 結果回填。參數用 Schema；**宿主先取得同意才執行；工具描述不可盲信**。

**toolSpec vs MCP**

| 項目     | toolSpec（Bedrock Converse）   | MCP Server                |
| -------- | ------------------------------ | ------------------------- |
| 綁定     | 綁在你的迴圈                   | 契約可跨宿主              |
| 適合     | 單應用夠用                     | 多 Host 重用              |

**迷思澄清框**

**上了 MCP 就比較高級？**

- ✗ 一定要把工具都包成 MCP，才算正式架構
- ✓ 先把描述寫對；單應用用 toolSpec 即可，跨宿主重用再上 MCP

> 一句話：MCP 的價值是接口重用，不是換一件馬甲。

## 五、工具設計原則：模型看得懂才叫好工具

- 模型只看名稱與描述，看不到你的實作原始碼；叫錯工具或填錯參數，整段軌跡作廢；回傳會進脈絡，太長或含糊的回傳下一輪更糊

| 項目     | 原則                                         |
| -------- | -------------------------------------------- |
| name     | 動詞＋名詞，如 `cancel_order`                |
| description | 寫清「做／不做／何時叫」                  |
| 參數     | 少而硬，枚舉優於散文                         |
| 回傳     | 短 JSON，避免整頁 HTML、長日誌或沉默         |
| 錯誤     | 錯誤碼＋下一步                               |

**合格範例 `get_order`（A1042）**

- 做：回傳狀態與出貨日
- 不做：不退款、不猜缺資料
- 參數：`order_id`（必填）
- 錯：`ORDER_NOT_FOUND` → 確認編號

**Quiz**：設計給模型呼叫的工具最關鍵 → **清楚的名稱、描述與 JSON Schema 參數**；業務規則應進工具契約、回傳太長會灌爆脈絡、規格要求使用者同意。

> 一句話：模型看不懂的描述，就是壞描述。

## Takeaway

1. 單迴圈加工具是預設；隔離、權限、可驗證三閘門都過才拆多 Agent
2. 選拓撲先問誰決定下一步，控制權越集中越好測
3. 交接物短、結構化、可驗證，禁止帶思考過程與成本
4. MCP 價值是接口重用；工具要有動詞名稱、做／不做、硬 schema、短回傳、可行動錯誤
