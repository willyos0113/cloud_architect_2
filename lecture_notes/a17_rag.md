# a17 | RAG：能跑很容易，能用要靠評估

> 來源：`lectures/A17-RAG.pdf`（共 39 頁；講義日期 2026-10-22；成本為講義查閱 us-east-1 的 OpenSearch／S3 Vectors 定價；出處為 RAG 原始論文 arXiv 2005.11401、Bedrock User Guide）

**今日目標**：機器人說「豆花七天內可以退」，店規寫的是「生鮮不接受退貨」——學會先診斷是哪裡壞（沒查到／查錯／沒用上），一次改一項，用分數驗證。

**六個名詞**

| 名詞                   | 意思                                               |
| ---------------------- | -------------------------------------------------- |
| RAG                    | 先查資料，再照著答                                 |
| chunking（切塊）       | 把長文件剪成一段一段，每段要能單獨看懂             |
| embedding（嵌入）      | 把一段文字變成一串數字（向量），意思相近座標就靠近 |
| top-k                  | 取離問題最近的 k 段交給模型                        |
| recall / precision     | 召回率（問漏）／精確率（問雜）                     |
| faithfulness（有據性） | 回答有沒有照著段落，沒亂加                         |

---

## 一、為什麼要 RAG：三個理由

| 理由     | 說明                                                     |
| -------- | -------------------------------------------------------- |
| 知識更新 | 模型知識會過期；改店規只要換文件、重新同步，不用重新訓練 |
| 可溯源   | 回答附上出處，人可以點進去核對                           |
| 成本     | 只放查到的幾段，比整本手冊塞進去便宜                     |

- 和 A16 的關係：把「查知識庫」包成一個工具，查到的段落放進脈絡，模型照著答

**兩條線：先建索引，再檢索生成**

| 時機       | 流程                                               |
| ---------- | -------------------------------------------------- |
| 事先做一次 | 文件（S3 等）→ 切塊 → 嵌入 → 存進向量資料庫        |
| 每次提問   | 問題 → 嵌入 → 找最近 k 段 → 問題＋段落交給模型回答 |

- **兩邊要用同一個嵌入模型**，座標才對得上
- 實作附檔用迷你版向量（概念是字詞統計），在你電腦上算、不花錢

**CCP 考點**

- 在 S3 文件內搜尋文字內容 → **Amazon Kendra**；Rekognition 分析圖片影片、Polly 文字轉語音、Lex 聊天機器人是誘答（題庫第 0320 題）

> 一句話：RAG 讓模型每次回答前先翻最新的資料，改文件不用重訓。

## 二、切塊與向量檢索：先切段，才查得到段

**三種切法**

| 策略     | 做法                           | 代價           |
| -------- | ------------------------------ | -------------- |
| 固定長度 | 每 N 個 token 切一刀，可設重疊 | 可能剪斷一句話 |
| 語意     | 在意思轉換的地方切             | 要多付模型費   |
| 階層     | 比對小段，交給模型時換成大段   |                |

**切錯的後果：例外被切到下一段**

- 原文：「生鮮與冷藏商品（豆花、仙草、豆漿）因衛生因素不接受退貨，**除非商品本身有瑕疵**；有瑕疵請在收到當天拍照並聯絡客服」
- 附檔預設每 20 字切一刀 → 「除非有瑕疵」被切到下一段，只拿到前一段就會漏掉例外
- 改成照段落切（`CHUNK_MODE=paragraph`）→ 整句一起回來
- **太大也不行**：一段塞太多主題，向量被稀釋，交給模型的雜訊變多

> 一句話：切塊要保住意思，太碎剪斷例外，太大稀釋向量。

## 三、三種失敗模式：先分清楚是哪一種

| 失敗     | 症狀                       | 附檔實例                                                                             | 修在哪 |
| -------- | -------------------------- | ------------------------------------------------------------------------------------ | ------ |
| 沒查到   | 答案那段沒被撈到           | 問「豆花可以退貨嗎？」，每 20 字切，例外在下一段                                     | 檢索   |
| 查到錯的 | 撈到別份文件，照錯的答     | 問「中秋禮盒可以退貨嗎？」，過濾猜錯分類，只撈到生鮮退貨政策（D01），該看的 D10 被擋 | 檢索   |
| 沒用上   | 段落給了，模型還是照印象答 | 問「可以用 LINE Pay 嗎？」（假設情境），段落寫只有三種付款方式，模型照常識答「可以」 | 生成   |

- 檢查點：外島冷藏題，段落明明寫「外島不提供低溫宅配」模型卻答「可以」→ **檢索到但模型不用（生成失敗）**，修法是要求只根據資料回答並標出處；換嵌入模型修的是檢索，這題檢索沒壞

> 一句話：RAG 答錯先診斷是查壞還是答壞，再對症下藥。

## 四、改善手段與評估

**四個改善工具：一個工具修一種壞**

| 工具     | 修什麼                                           | Bedrock 對應        |
| -------- | ------------------------------------------------ | ------------------- |
| 混合檢索 | 向量分不清細節、編號、型號（向量＋關鍵字一起找） | `HYBRID` 搜尋類型   |
| 重排序   | 最相關的那段排在後面（先多撈再用模型重排）       | reranker 模型       |
| 查詢改寫 | 一題問兩件事只查到一件（拆成小問題）             | query decomposition |
| 標籤過濾 | 撈到別的分類的文件（只在某分類找）               | metadata 過濾       |

**用分數驗證：一次改一項，每次重跑（講師參考值，只跑檢索、不連 AWS）**

| 設定                              | 命中率              | 精確率      |
| --------------------------------- | ------------------- | ----------- |
| 原設定（每 20 字切、向量、k=5）   | 30%                 | 61%         |
| ① 改照段落切                      | 100%                | 54%         |
| ② 再改只交 3 段（`TOP_K=3`）      | 90%                 | 80%         |
| ③ 再加混合檢索（`SEARCH=hybrid`） | 100%                | 70%         |
| ④ 再加重排序（`RERANK=True`）     | 100%                | 80%         |
| 另一路：② 加過濾（`FILTER=True`） | 90%（20 題漏 2 題） | 88%（最高） |

- 改善常是**一項變好、另一項變差**（例：照段落切命中率升、精確率降）
- 過濾那一路精確率最高，但猜錯分類會整個漏掉（2 題）

**評估：檢索和生成分開算**

| 層次 | 指標                   | 意思                         |
| ---- | ---------------------- | ---------------------------- |
| 檢索 | 召回率（recall）       | 該撈到的段落，撈到幾成       |
| 檢索 | 精確率（precision）    | 撈回來的段落，幾成真的相關   |
| 生成 | 有據性（faithfulness） | 回答有沒有照著段落，沒亂加   |
| 生成 | 相關性、正確性         | 有沒有回答到問題、答得對不對 |

- Bedrock 只評檢索的指標：context relevance、context coverage；檢索＋生成的還有 correctness、faithfulness、citation precision 等
- **先看檢索分數**：檢索沒撈到，生成再好也答不出來
- 實作簡化版：命中率 ≈ 召回率（段落裡有沒有答案原文），精確率看是不是來自正確文件
- 檢查點：相關 2 段、撈回 4 段其中 1 段相關 → 召回率 1/2 ＝ 50%、精確率 1/4 ＝ 25%（口訣：召回率問漏、精確率問雜）

**自動判分：便宜，但要抽查**

- 程式印四個數字：檢索命中率、檢索精確率、回答正確率（有沒有指定關鍵字）、引用正確來源
- 會判錯：Q13「可以用 LINE Pay 付款嗎？」回答「目前提供三種付款方式…[D05]」，程式找不到「不」「只」「沒有」判錯，人看是有據且等於回答「不能」→ 要抽查

> 一句話：一個工具修一種壞，一次改一項，檢索與生成分開評。

## 五、託管與手刻：省事，換掉旋鈕

| 項目   | 託管知識庫（Bedrock Knowledge Bases）           |
| ------ | ----------------------------------------------- |
| 事先   | 按同步，就讀檔、切塊、變向量、存起來            |
| 提問   | 一個 `RetrieveAndGenerate`：檢索、生成、附出處  |
| 拿走的 | 切塊只能選內建策略，自訂要先自己切檔或寫 Lambda |
| 限制   | 混合檢索只支援部分向量資料庫                    |

**同步與成本：最低消費差很多**

- 文件有增刪改就要同步（增量，只處理變動的檔案）；可用 EventBridge Scheduler 排程呼叫 `StartIngestionJob`

| 向量儲存（us-east-1，講義 2026-10-22）     | 成本                                                                       | 適合       |
| ------------------------------------------ | -------------------------------------------------------------------------- | ---------- |
| OpenSearch Serverless（Classic 集合）      | 最少 2 OCU × $0.24 × 730 小時 ≈ **每月 350 美元，閒置也算**（1 OCU ≈ 175） | 高頻查詢   |
| OpenSearch Serverless（NextGen／開發測試） | 閒置可縮到 0                                                               | 開發測試   |
| Amazon S3 Vectors                          | 儲存 $0.06／GB／月，查詢另計；一萬段向量約 40 MB，不到 1 美分／月          | 查詢不頻繁 |

> 注意：本專案月預算 30 美元，開 OpenSearch Serverless Classic 集合一個月就爆預算；學習用請選 S3 Vectors，並以官方定價為準再確認。

**CCP 考點**

- 描述 S3 核心功能 → **物件儲存**，提供高效能、安全性、可擴展性與資料可用性；區塊儲存是 EBS、SMB 檔案系統是 FSx、彈性 NFS 是 EFS，都是誘答（題庫第 0179 題）；S3 Vectors 把向量放進 S3 向量儲存桶，沿用按用量付費

> 一句話：託管省事但少旋鈕，向量儲存選對，月費差一千倍。

## 六、Agentic RAG：模型自己決定查不查

- 把查知識庫包成 `search_kb` 工具，由模型決定要不要查、查幾次
- 打招呼可能不查，一題兩問可能查兩次
- **代價：呼叫變多，要保留輪數上限**
- 離線範例（`agentic.py --offline` 假模型照劇本）：問「豆花可以退貨嗎？運費多少？」→ 第 1 輪查退貨、第 2 輪查運費、第 3 輪附出處 `[D01]`、`[D02]` 回答；查 2 次、呼叫模型 3 次
- 換真模型次數可能不同，問「你好」看它會不會乾脆不查
- 註：講義提到 Bedrock Agents Classic 已不開放新客戶

**AI 連結：AI 出題，你來篩**

- AI 出候選題，你分成留下、修改、丟掉
- AI 打分，你抽查它評錯哪幾題
- AI 用提問引導你分辨檢索或生成失敗

## 七、實作：把一個爛掉的 RAG 修好

> 附檔是故意做壞的 RAG（`rag.py` 每格一個旋鈕 CONFIG），10 份店規、20 題評估集已備好；檢索評估不連 AWS，`--llm` 才呼叫模型（花抵用金）；**沒有建立任何資源，不用刪**。壞在三處：切太碎、沒重排序、沒要求引用。

**必做步驟：先診斷，再一次改一項**

1. **準備**：建虛擬環境、裝 boto3；`aws configure list --profile course`
2. **跑基準**：`python3 rag.py eval`，再跑 `python3 rag.py eval --llm`（真模型）；基準命中率 30%（6/20）
3. **看壞掉的題目**：`python3 rag.py ask "豆花可以退貨嗎？"`，看每段文件編號，答案原文在不在裡面
4. **至少改兩項，一次一項**：例如 `--set CHUNK_MODE=paragraph`，再試 `SEARCH=hybrid`、`TOP_K=3`
5. **把最後設定寫回 CONFIG（含 `CITE=True`）**，再跑 `eval --llm`，抽查三題判分
6. **交 REPORT.md**：前後分數＋程式印出的完整輸出，**分數要能重現；你的報告只能貼自己跑出來的**（上表為講師參考值）

**加碼與收尾**

- Agentic RAG：`python3 agentic.py --offline "豆花可以退貨嗎？運費多少？"`，再拿掉 `--offline` 問「你好」
- AI 連結：請 AI 出 5 題候選題，自己篩選修正並寫下丟掉的理由
- 收尾：Billing 主控台看抵用金

## Takeaway

1. RAG 能跑很容易，能用要靠評估
2. 切塊保住意思；先分清三種失敗（沒查到／查錯／沒用上），一個工具修一種壞
3. 檢索與生成分開評，召回率問漏、精確率問雜，自動判分要抽查
4. 向量儲存選對：OpenSearch Serverless 有最低消費，S3 Vectors 按用量
